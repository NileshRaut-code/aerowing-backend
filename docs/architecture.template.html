Tenant isolation architecture

Each vendor's data stays isolated and correct, and developers write as little code as possible to keep it that way. Each vendor runs on its own VM, which carries its tenant id in its environment. All VMs share one MongoDB. One Mongoose plugin scopes every query automatically, so business code never writes a tenantId filter.

1 vendor = 1 VM TENANT_ID from env, never client single MongoDB auto-scoping plugin fail closed

06Authenticated request: list users

Every list endpoint follows the same contract: page, pageSize, search, sortBy and sortOrder in the query, and { items, pagination } in the response.

{{M5}}

The search text is regex-escaped, sortBy must be on an allowlist, and pageSize is at most 100. _id is the tie-breaker, so ordering is stable. The response returns only the table's DTO fields.

07How isolation is enforced

The tenant plugin is on every tenant-owned model, so there are no manual tenantId filters anywhere in business code.

{{M6}}
Defence in depth
  1. Zod rejects any tenantId the client sends.
  2. The tenant comes only from the env pin.
  3. The JWT audience is bound to tenant:<id>.
  4. The plugin filters every DB operation and fails closed.
  5. Compound indexes start with tenantId.
Known limits
  1. Model.collection or the raw driver bypasses the plugin. It is forbidden by convention, so add a lint rule for it.
  2. await queries inside the scope. A query returned un-awaited runs outside the scope and is rejected.

09Issue alerts (Slack / mail)

emitIssue() never throws back into the caller, and a notifier failure is only logged. Slack and mail are dummy functions for now. To go live, replace the bodies of sendSlack and sendMail.

10Batch jobs

Each job run holds a lock, runs in its tenant's scope, processes data in chunks and retries on failure. Job handlers must be idempotent. On SIGTERM, the runner stops scheduling and waits for in-flight runs to finish.

12Adding a tenant feature (e.g. Booking)

Isolation, the error envelope, alerts and pagination come automatically. You write four small pieces.

  1. models/booking.model.js: add schema.plugin(tenantPlugin) and an index starting with { tenantId: 1, … }. Store money as integer amountMinor plus currency.
  2. controller/booking.controller.js: write strict Zod schemas and thin handlers, and use paginate() for the list. Never write a tenantId filter.
  3. utils/permissions.js: add the permission keys and map them to roles.
  4. routes/vendor.routes.js: wire each route as authorize(P.X), validate({…}), handler, after requireUser.
